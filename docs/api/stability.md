# API stability and the OpenAPI snapshots

The v1 API is a contract. Two checked-in OpenAPI documents pin it, and a smoke
test fails the build when a route that is part of the contract changes shape.

| File | What it is | Generated by |
|---|---|---|
| `docs/api/openapi-v1.stable.json` | The **core** API: every route a build with `modules/` deleted serves, with components. | `python -m backend.scripts.dump_openapi --profile core --full …` |
| `docs/api/openapi-v1.full.json` | The **full** API: the core routes plus the ones the modules registration mounts. | `python -m backend.scripts.dump_openapi --profile full --full …` |
| `frontend/src/tests/fixtures/openapi.json` | Paths and methods only, for the dashboard's URL-literal guard (`frontend/src/tests/services/url-literals.test.ts`). A **full** dump: the guard subtracts `openapi.module-paths.json` from it for a core run, so a core dump here would make it subtract them twice. | `python -m backend.scripts.dump_openapi --profile full …` |

`make openapi` regenerates all three. `--profile core` hides the `modules`
package from the import system before the application is imported, so the core
document can be produced from a full checkout; it is byte-identical to the
document a tree with `modules/` deleted produces (`scripts/core_build.sh`
checks that tree the long way round). `--profile full` requires the modules
registration to load and fails otherwise.

## The rule

`backend/tests/smoke/test_openapi_snapshot.py` regenerates the live documents
in a fresh interpreter and compares them with the snapshots:

- A path/method in the snapshot that is **stable** must still exist, and its
  operation object — parameters, request body, responses, and every component
  schema those reference, transitively — must be identical. Any difference
  **fails** the smoke suite.
- A path/method marked **beta** may change or disappear: the test **warns**
  instead.
- A path/method that exists but is not in the snapshot yet is a warning too:
  run `make openapi`, commit the result, and decide whether it is beta.
- `openapi-v1.full.json` must be a superset of `openapi-v1.stable.json`, and the
  module-only paths must be exactly the list in
  `frontend/src/tests/fixtures/openapi.module-paths.json`, so the three fixtures
  cannot drift apart. That fixture is maintained by hand.

Every route is stable by default. Stability is a promise about the *shape* of
the route — its URL, parameters, request and response schemas — not about its
behaviour.

## Marking a route beta

Stability is declared on the route, in the OpenAPI document itself, with the
`x-stability` extension, so the snapshot carries it and the test can read it
without a side table:

```python
@router.post(
    "/experiments/{experiment_id}/something-new",
    response_model=SomethingNewResponse,
    openapi_extra={"x-stability": "beta"},
)
def something_new(...):
    ...
```

`openapi_extra` is merged into the operation object by FastAPI, so the
snapshot shows `"x-stability": "beta"` on that method. Only the value `beta`
means anything; leave the key off a stable route. Promoting a route is deleting
the line and regenerating the snapshots.

Use beta for a route whose request or response is still being shaped by real
use — a new analysis endpoint, a first cut of a bulk operation — and take it
off once a released SDK or the dashboard depends on it.

## Changing a stable route

Do not. Add a new route (mark it beta while it settles) or bump the API
version. If a change to a stable route is unavoidable — a security fix that
has to remove a field, say — regenerate the snapshots with `make openapi`,
and say in the pull request which stable operations changed and why; the
smoke test's failure message lists them by method and path, with the first
differing keys.

## Profiles

The core snapshot is the public promise: it must not change with the set of
installed modules. That is why the statistics (Bayesian, CUPED, sequential
testing) are core and not a module — a results response whose shape depended
on an optional module could not have one stable document (see the manifest,
`modules-manifest.txt`, "DELIBERATELY NOT IN THIS MANIFEST"). The three routes
that exist in both profiles but answer 501 in the core profile without the
module body (`/compliance/reports/{standard}`, `/compliance/export`,
`/experiments/{id}/split-url/preview`) are in the core snapshot, because their
URL and shape are.
